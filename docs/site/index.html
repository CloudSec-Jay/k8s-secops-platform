The brief

The goal is not simply to make Wazuh pods healthy. The system needs an explainable path from a Linux endpoint, through a controlled network boundary, into searchable evidence and an operator response.

A Hyper-V virtual machine runs the control plane and two bare-metal laptops run the workloads, all on one home LAN. One Ansible entry point prepares and bootstraps them, Cilium networks them in eBPF mode with SELinux enforcing, and the upstream Wazuh stack runs on replicated Longhorn storage. Every version is pinned, and the incidents met along the way are written up below.

01

The infrastructure map

Cilium replaces kube-proxy entirely: kubeadm skips the addon/kube-proxy phase and service routing happens in eBPF. Hubble exposes the resulting flows so policy can be built from observed behavior instead of assumptions.

Every node has its own address on the home LAN. The control plane is a Hyper-V VM on an External switch and the workers are laptops on Wi-Fi, so kubelets, the API server, and Cilium reach each other directly. The earlier build ran every node as a libvirt VM behind NAT on a Wi-Fi host and joined the two networks with proxy ARP and port forwarding; that layer is now retired. Services opt in to a LAN address by label and a worker answers ARP for it, so the indexer never receives one.

SELinux stays enforcing and containerd labels every container. kubeadm patches run only the four control-plane static pods as spc_t; every workload pod stays confined as container_t.

Every pod in every namespace starts in default deny. The allow rules were written from captured Hubble flows on the earlier build and are re-applied one namespace at a time on the rebuild. DNS is limited to the names each workload needs, CoreDNS may reach only the home router, and the managers reach the vulnerability feed by FQDN rather than by IP range.

Wazuh receives endpoint events, applies reviewed rules and decoders, retains searchable security data, and gives the operator a place to investigate.

02

One path from empty host to running stack

  1. PowerShell

    Control-plane VM

    A re-runnable script creates a Gen 2 Hyper-V VM on an External switch with static memory, the UEFI CA Secure Boot template, and checkpoints off.

    scripts/HyperV/
  2. Ansible · 1

    Prepare nodes

    Static node addresses and router DNS, hostnames from the inventory, containerd with systemd cgroups and SELinux labels, swap off, and held kubeadm packages.

    cluster-setup.yaml
  3. Ansible · 2

    Laptops as servers

    The lid switch is ignored, every sleep target is masked, the console blanks after 60 seconds, and Wi-Fi power saving is off.

    baremetal-prep.yaml
  4. Ansible · 3

    Form the cluster

    kubeadm init without kube-proxy and with spc_t patches for the control plane. A re-run checks /readyz and stops on a half-finished init.

    kubeadm-bootstrap.yaml
  5. Ansible · 4

    eBPF dataplane

    Helm v4.3.1, SHA-256 verified, then Cilium 1.20.2 from the OCI chart with reviewed values and a wait for the node to report Ready.

    cilium-install.yaml
  6. Ansible · 5

    Replicated storage

    Longhorn becomes the default StorageClass with one replica per laptop, on each worker's encrypted disk.

    longhorn-node-prep.yaml
  7. Runbook

    Wazuh workload

    Upstream Wazuh v4.14.8 with a Kustomize overlay that maps wazuh-storage to the cluster's StorageClass.

    platform/wazuh/

ansible-playbook site.yaml -K runs stages 1 to 4 in dependency order; storage and the platform add-ons follow as separate playbooks once Cilium is healthy.

04

What broke, and why

INC-01 / STORAGE

PVCs stuck Pending

The upstream overlay pointed wazuh-storage at a MicroK8s provisioner that does not exist here.

Fix: a Kustomize patch to rancher.io/local-path with WaitForFirstConsumer.
INC-02 / NETWORK

Image pulls timing out

DNS returned IPv6 addresses for the registry CDN, but the libvirt bridge is IPv4-only, so pulls stalled before falling back.

Fix: traced through kubelet events; the pull completed over IPv4 with cached layers kept.
INC-03 / CAPACITY

Eviction loop on worker-2

Vulnerability feeds, images, and the OS filled a 30 GiB disk. Kubelet tainted the node, and node-pinned volumes left the pod nowhere to go.

Fix: online resize to 60 GiB with virsh blockresize and growpart, then Terraform reconciled.
INC-04 / STARTUP

Dashboard login timeout

The dashboard's 20-second API call reached the manager while its REST API was still cold-starting after the resize.

Fix: confirmed from dashboard logs; requests returned 200 in about 200 ms once the API was up.
INC-05 / RECOVERY

Power loss split the manager cluster

After the host lost power, every pod returned to Running, but the worker could not resolve the master: Cilium's DNS proxy dropped the lookup because * never crosses a dot. The rule was written from observed flows, and this lookup only happens on reconnect. New agents enrolled but were rejected as unknown.

Fix: explicit DNS patterns for the cluster name; the worker rejoined on its next retry and the agent went active.
INC-07 / SELINUX

Control plane crash-looped

With container labeling on, etcd, the API server, the scheduler, and the controller manager ran as container_t, which the policy denies reading kubernetes_file_t. Each could not open its own keys and restarted; audit.log showed the denials.

Fix: kubeadm patches run only those four static pods as spc_t; SELinux stays enforcing and workload pods stay confined.
INC-08 / IDEMPOTENCY

A re-run would skip a failed init

kubeadm writes admin.conf before the step that failed, and the init task used creates: admin.conf, so a re-run would have skipped init and continued against a dead control plane.

Fix: init is gated on the API server's /readyz; a half-finished init now stops the play with reset instructions.
INC-09 / PRIVILEGE

Helm vanished under sudo

Helm in /usr/local/bin ran for the admin user, but Rocky's sudo secure_path omits that directory, so every privileged Helm task failed with no output.

Fix: one helm_binary variable with the full path, used by the install check and every Helm module call.

INC-01 to INC-05 come from the earlier libvirt build (INC-06, Longhorn under default deny, is in the case study); INC-07 to INC-09 come from the hybrid rebuild. Read the full case study ↗

06

Current state

Cluster rebuilt.
Wazuh next.

The lab moved from three libvirt VMs to a hybrid cluster: a Hyper-V control plane and two bare-metal laptop workers. All three nodes are Ready, Cilium is healthy with kube-proxy replacement, and both workers came back from a drain-and-reboot drill with their lids closed (observed 2026-10-26).

The earlier build reached an enrolled endpoint with alerts on the dashboard, and an unplanned power loss tested its recovery (INC-05). Those results have not yet been repeated on the new nodes.

Next: apply the network policies, install Longhorn, redeploy Wazuh, re-enroll an endpoint, fire a deliberate, harmless test event end to end, and commit redacted evidence for each step.
